# Initial-authoring and editorial review experiments

Status: owner authorized research and comparative experiments on September 18, 2026, and explicitly approved committing and deploying the verified copy/context candidate for private tests. This is an experiment-only exception to the no-automatic-critic doctrine, **not approval to install production orchestration**. Astra remains coordination/audit only; author/reviewer API calls use Luna or Sol. No customer site is published.

## Decision to make

Does a second perspective improve the final customer-facing content enough to justify its cost and failure modes, or are better first-pass guidance / one stronger editor sufficient? A poor reviewer in one test does not establish that review cannot work. Conversely, a plausible critique does not establish that following it improves the page.

Research uses primary papers and official platform documentation, distinguishing public behavior from undisclosed internal architectures. Existing facts, immutable source, asset provenance, trusted runtime and deterministic release gates remain unchanged. Only real accuracy, capability, security and functional violations block production; subjective editing preferences remain advisory.

## Controlled editorial screen

Use the exact corrected Pristine and HD packets, photographs and example-led Luna drafts from the preceding experiment. No new crawl, cherry-picked hand repair, or evaluator answer sheet enters the model context. Each business has the same starting draft across five candidates:

1. Unchanged draft (zero calls).
2. Luna revises once using the source and neutral editorial criteria.
3. Sol directly edits once using those same inputs, without a separate critique.
4. Sol reviews the draft against source; Luna revises once with that feedback.
5. Sol revises once with the **same** Sol feedback from candidate 4.

Ten total calls across two businesses, maximum two concurrent, conservative catalog admission below $8. Same source/pixels/authority, high reasoning and output shape; no loops, retries or automatic winner selection. The critique may be empty, and revisers must reject unsupported advice. Preserve correct ordinary service scope, useful technical qualifications, exact contacts and genuine business distinctions. Do not erase supported material merely because it contains a sensitive keyword. Reviewer findings must point to specific text/image decisions and supporting evidence; there is no quality score or quota of defects.

Root reviews randomized final candidates before reading arm labels or reviewer feedback. Record improvements, remaining defects, regressions, contact/action preservation, false review findings, latency and cost. Count the original drafting cost when comparing complete pipelines, not just the cheap final revision. Existing direct-Sol drafts are descriptive context, not newly randomized replications. This small screen identifies candidates and mechanisms, not reliability percentages or conversion lift.

## Full-site validation

Investigate the existing private hosted canary and ordinary edit paths before adding any tooling. Candidate local context/skill changes cannot be called deployed or tested end-to-end until normal release and exact identity verification occur. A current-release Luna/Sol comparison and one explicitly requested edit may still test present-day end-to-end author/editor capability; label that configuration precisely rather than implying local patches are present. Preserve original unassisted candidates and distinguish assisted edits from initial-generation success.

Use the same one or two retained businesses and input lineage. Review actual desktop/mobile rendering, full route inventory, meaningful service/package coverage, natural copy, photo attribution/placement, Google rating/link when supplied, navigation, forms and final release-gate evidence. No private canary is published or sends notifications. Stop on a shared material problem and diagnose it rather than spend a broad batch. Production release/commit authority, if needed beyond testing, must remain explicit under repository rules.

## Decision rule and non-goals

- Prefer the simplest candidate with a clear observed gain and no material regression. Do not promote from a single attractive response.
- If direct Sol editing matches reviewed editing, the separate reviewer has not earned its place.
- If review adds valid useful signal and the reviser reliably preserves correct content, consider one bounded editorial handoff—but require a separate product decision and whole-site evidence before installation.
- If all arms share the same failure, investigate evidence delivery or the task boundary instead of assuming another agent fixes it.
- No production critic, conditional escalation classifier, per-route agent swarm, new queue, framework, presentation gate, token counter, or automatic repair continuation is added in this work block.
